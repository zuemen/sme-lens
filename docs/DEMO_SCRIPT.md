# 決賽 Demo 演示腳本 — 企鏡 SME Lens：財報看不到的集團結構

> 對應提案書主打情境：企業關係圖揭露財報看不到的集團曝險與資金結構。建議演示時間：
> 3–3.5 分鐘（嵌入 8 分鐘簡報的中段）。授信與集團歸戶是本次參賽的主線，出金審查
> （防詐分支）留在最後當「同一引擎能跨場景」的證據，不是第二個產品。
>
> **三種演示方式**（三層備援，見「全離線演示程序」一節的完整說明）：
> - **網站版（預設）**：全程在瀏覽器完成，不需要開終端機。見下方「網站版演示前準備」。
> - **全離線程序（會場無網路時，涵蓋全部五步）**：本機跑 API＋本機建置前端，
>   五步全部能講，見下方「全離線演示程序（會場無網路時）」。**這是第 1–4 步
>   （授信＋集團歸戶）在無網路時真正的保險網，不是 Streamlit。**
> - **Streamlit 本機版（備用，只涵蓋出金審查）**：`smelens/app/workbench.py` 目前只有
>   「出金審查 Demo」與「金流圖譜工作台」兩種模式，**沒有**授信意見書或集團歸戶頁面。
>   只有在連上面兩種方式都失敗（例如本機 Python 環境也壞了）時才退到這裡，只能講
>   第 5 步。

## 全離線演示程序（會場無網路時）

本機跑後端 API＋本機建置並啟用前端，五步全部能講，**不需要任何網路連線**。已於
本機實際跑過一次全流程（`uvicorn` + `vite build` + `vite preview`），確認可行。

### 事前準備（務必在還有網路時做完，到會場前完成，會場現場做不了）

```bash
cd web
npm ci
```

`npm ci` 需要連到 npm registry 下載套件，會場沒有網路一定失敗——**必須在出發前
做好**，讓 `web/node_modules` 已經存在。

### 會場現場執行順序（無網路可跑）

1. 開一個終端機，啟動本機 API（在 repo 根目錄）：

   ```bash
   cd /c/Users/sanketsu/sme-lens
   ./.venv/Scripts/python.exe -m uvicorn smelens.api.main:app --port 8000
   ```

   看到 `Uvicorn running on http://127.0.0.1:8000` 即可，這個終端機留著別關。

2. 開第二個終端機，**用剛剛那個本機 API 的網址建置前端**：

   ```bash
   cd /c/Users/sanketsu/sme-lens/web
   VITE_API_BASE=http://localhost:8000 npm run build
   ```

   **`VITE_API_BASE` 是建置時就烤進 JS 檔的（build-time，不是 runtime）**——這一步
   之前踩過坑：如果建置時沒指定或指到錯的網址，事後改環境變數沒有用，網頁還是打
   舊網址，只能重新 `npm run build` 一次。所以順序一定是：先確定本機 API 網址
   （步驟 1 的 `http://localhost:8000`），才做這一步的建置。

3. 啟動預覽伺服器：

   ```bash
   npm run preview
   ```

   終端機會印出實際網址，例如 `Local: http://localhost:4173/`——**如果 4173
   已被占用，Vite 會自動換一個 port 並印出實際用的那個，照終端機印出的網址開，
   不要死背 4173。**

4. 瀏覽器開終端機印出的那個網址（例如 `http://localhost:4173/`），照「演示動線」
   五步正常操作即可。

### 會降級與不會降級的部分

- **會降級（純美觀，不影響操作）**：頁面字體來自 Google Fonts
  （`fonts.googleapis.com`／`fonts.gstatic.com`，見 `web/index.html` 的
  `<link>` 標籤）。無網路時瀏覽器連不上，會自動退回系統字體——畫面字型會跟平常
  看到的不一樣，這是預期行為，presenter 不用緊張，不影響任何按鈕或數字。
- **不會降級**：檢查過 `web/src/api/client.ts`、`web/vite.config.ts` 與
  `web/index.html`，前端唯一會打的網路請求是 `VITE_API_BASE` 指到的 API
  （`/health`、`/credit`、`/group`、`/screen`、`/graph` 等端點）——這一步已經
  在步驟 2 指到本機 `http://localhost:8000`，其餘沒有任何外部 API 呼叫、CDN
  依賴或遙測。本機驗證：`curl http://localhost:8000/health` 回
  `{"status":"ok"}`，`npm run preview` 建置出的頁面 HTML／JS 內建的 API 位址
  確實是 `http://localhost:8000`（用 `grep -o http://localhost:8000
  dist/assets/*.js` 驗證過）。

## 演示動線（口白 ＋ 操作）

### 第 1 步：拋出問題（口白，約 20 秒）

> 「銀行核貸看什麼？財務報表、擔保品、聯徵紀錄。這三樣東西，中小企業要嘛做不漂亮、
> 要嘛沒有擔保品可押。可是有一件事，這三樣東西**從來不會告訴你**：這家公司的錢，
> 進進出出，到底跟誰綁在一起。企鏡 SME Lens 做的就是這件事——把轉帳流水跟企業登記
> 關係畫成一張關係圖，讓報表看不到的結構浮出來。」

### 第 2 步：授信意見書 — 泰昇精密（操作，約 70 秒）

- 開 `/credit`，申請企業維持預設「泰昇精密（申請人）」→ 按「產生授信意見書」
- 先指著畫面上最大的那行字——「建議」區塊，念出：

> 「泰昇精密申請週轉金貸款，財報健康、無退票紀錄。系統給的建議是：**建議暫緩核貸，
> 先行實地查核關係人交易與主要買方合約之真實性**。這句話是畫面上最大的字，也是行員
> 真正會照著做的動作——不是一個分數，是一個行動指令。」

- 捲到「授信關注等級」卡片，念三個數字：

> 「往下看證據：關注分數 0.82，落在『關注』等級；網絡信用分只有 0.5667。這不是憑空
> 給的——命中了兩個企金風險圖樣。」

- 捲到「命中企金風險圖樣」與「企業關係圖譜」，指出封閉資金環與買方集中：

> 「第一個：**封閉資金環**——泰昇精密 → 宏益企業 → 昇泰貿易 → 泰昇投資 → 泰昇精密，
> 錢繞了一圈又流回申請人自己手上。這個環上有一段是宏益企業經手的過水——宏益企業
> 流入 600 萬、流出 594 萬，過水比 99%，是典型的空殼中介；但泰昇精密身處這個環中，
> 並不是這段過水的發動者，它是環上被捲進來的一環，這是頁面上如實呈現的三方關係，
> 不是誰誣賴誰。第二個：**買方集中**——收入 3,140 萬裡有 84% 來自單一買方鴻寶電子，
> 客戶集中度風險偏高，主要買方一旦出事，泰昇精密的現金流就斷了。這兩件事，財報上
> 一個字都看不出來。」

### 第 3 步：集團歸戶 — 全場最強的一段（操作，約 55 秒）

- 開 `/group`，按「執行集團歸戶」，先指申報名冊，再指「申報 vs. 實際」卡片：

> 「客戶申報了兩個獨立集團：泰昇集團（泰昇精密＋泰昇投資，申報曝險 4,200 萬）、
> 昇泰集團（昇泰貿易，申報曝險 800 萬）——分別掛在兩個不同的授信限額底下計算。
> 按一下『執行集團歸戶』——關係圖比對董監事名冊後，這兩個申報集團**合併成一個**。」

- 指著「隱性關聯」卡片，點名王秀英：

> 「原因就一個人：**王秀英**。她同時是昇泰貿易的董事，也是泰昇投資的監察人——申報
> 名冊上這是兩家『不同集團』的公司，共用了同一個自然人，關係圖把它們併回同一個
> 集團。昇泰貿易的 800 萬曝險，本身就在申報書的曝險欄裡，銀行早就核貸入帳，肉眼看
> 得到——**看不到的是它跟泰昇集團同屬一個必須合併計算曝險的實體**。少了這條隱性
> 關聯，銀行法對這個集團的單一授信限額，比對到的只是申報的 4,200 萬，而不是併入
> 後真正該合計的 **5,000 萬**。這就是集團授信曝險超限最典型的發生方式——不是金額
> 造假，是集團歸屬漏報，而漏報的原因，肉眼比對董監事名冊根本抓不出來。」

### 第 4 步：對照組防守 — 禾昌五金（操作，約 20 秒）

- 回 `/credit`，切換申請企業為「禾昌五金（對照組）」→ 按「產生授信意見書」

> 「同一套引擎，換一家真的乾淨的公司：禾昌五金。關注分數 0.0584，等級正常，網絡
> 信用分 0.7078，**命中風險圖樣 0 個**。這一步很重要——如果這套系統看誰都像有問題，
> 那它就沒有訊號。它只在真的有結構異常的地方亮燈，這才是它可以被行員信任的原因。」

### 第 5 步：防詐分支 — 同一引擎跨場景（操作，約 25 秒）

- 開 `/screening`，目標地址保持預設 `TOtcOut01`、金額 500,000 → 按「執行出金審查」

> 「同一套圖引擎，換一組圖樣，就能拿去做虛擬資產防詐。這筆 50 萬 USDT 出金，
> 綜合風險 0.66，判定加強審查（EDD）。注意兩個分數：地址自身結構分數只有 0.15，
> 名單比對攔不住它；真正拉高風險的是關聯分數 0.60——它上游兩步之內就是一個集資
> 主錢包。正因為自身結構沒有異常，我們給的不是硬擋，而是加強審查（EDD）——這跟
> 第 2 步的『建議暫緩核貸』是同一種邏輯：把證據交給人覆核，而不是系統自己下最終
> 決定。」

## 預期 QA 與回應要點

| 可能提問 | 回應要點 |
|---|---|
| 資料是真的嗎？ | 泰昇精密／禾昌五金／集團名冊為內建合成情境圖（`smelens/`），供 Demo 與測試基準用；出金審查劇本圖比例與時間節奏參照 165 公開案例之假投資出金模式。真實資料接入（商業司開放資料建圖）列為後續計畫，未在本次範圍 |
| 集團怎麼歸戶出來的？為什麼不用社群偵測？ | 公司—自然人二部圖投影出公司關聯圖後，用**連通分量**（connected components）而非 Louvain 社群偵測做歸戶：集團歸戶要的是「誰在同一個必須合併計算曝險的實體」，這是法遵上的二元問題（合併／不合併），連通分量給出的是確定性、可稽核、不受解析度參數影響的答案；Louvain 這類社群偵測適合的是模糊的「風險群聚」場景（例如出金審查頁的社群風險比例），兩者用在不同問題上，不是互斥的取捨 |
| 關注分數是信用評等嗎？ | 不是。這是**關注等級**（watch／caution／normal），標記「這家公司的關係圖結構值不值得人工再看一次」，不是取代聯徵評等或信用評分模型；它進不了徵信報告的評等欄位，它進的是行員的複核清單 |
| GNN 在哪裡？為什麼線上看到的是規則分數？ | GNN（`models/gcn.py`／`models/sage.py`）目前只做**離線訓練與評估**，基準見 RESEARCH.md（Elliptic 資料集）；線上 API 現在提供的是規則式評分（中心性百分位＋圖樣命中），這是刻意的選擇——規則分數的每一項都能寫成一句中文敘事、指到圖上具體的節點和邊，GNN 分數目前做不到這件事。這本身就是解釋性優先於分數優化的論證，不是功能缺口 |
| 閾值怎麼定？ | 授信關注等級與出金審查風險分數的門檻為 Demo 預設；正式部署依業者風險胃納與歷史誤報率校準，並支援分層處置 |
| 誤報怎麼辦？ | 決策採分級處置（授信面是「建議暫緩核貸／得依既有條件辦理」，防詐面是「加強審查 EDD／放行」），不是一律直接拒絕；本案禾昌五金結構面無異常，給的是「得依既有授信條件辦理」，泰昇精密有結構異常，給的是「先行實地查核」而非「直接拒貸」——人在迴路中 |
| 換成真的銀行資料會怎樣？ | 圖結構與演算法完全不變：Demo 用的是內建合成情境圖，行內部署時把轉帳流水、票據資料接進來建同一張圖即可；股權關係層另可疊經濟部商業司公司登記開放資料。這是計畫拆分的「計畫 2」，本次繳交的是核心引擎（計畫 1） |
